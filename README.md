# 企业单据智能审核引擎

[![License](https://img.shields.io/badge/license-Apache--2.0-blue.svg)](LICENSE)
[![Python](https://img.shields.io/badge/python-3.11%2B-3776AB.svg)](https://www.python.org/)
[![FastAPI](https://img.shields.io/badge/FastAPI-0.115%2B-009688.svg)](https://fastapi.tiangolo.com/)

**给企业内网加一层能解释、能复核、能落地的 AI 审核。**

不聊天、不写文案、不做知识库问答。只做一件事：把一条业务单据的合规判断，
收敛成「通过 / 转人工 / 退回补正」三个结论，**每条结论都附制度条款和证据**。

---

## 它解决什么问题

企业里大量单据审核卡在同一个人手上——财务审报销、HR 审入职材料。
规则都写在制度里，但执行全靠人记：同样的单据不同的人能审出不同结果，
人一忙就只看金额不看依据。

直接把这件事交给大模型，业务方不敢用：结论不可复现、判错无法申诉、出事没人担责。

所以这套引擎的做法是——**把能算准的部分用代码锁死，只把真正模糊的判断交给模型。**

## 实际输出长这样

下面是真实运行 `python demo_hr.py` 的输出（非示意稿；mock 模式下完全离线，可复现）：

```text
------------------------------------------------------------------------------
材料包 RZ-2026-1102-018｜候选人 李思远｜部门 产品中心｜岗位 高级产品经理
用工形式 全职｜拟入职 2026-11-02｜材料 4/5 份已提交
------------------------------------------------------------------------------
审核结论：REJECT 退回补正   耗时 224 ms
命中 3 项高危不合规：必备材料齐全性、材料出具日期时效、材料证件号码一致性
------------------------------------------------------------------------------
[不通过] [HIGH] HR-003 材料出具日期时效  (置信度 1.00｜deterministic)
    说明：出具日期 2026-06-15 距入职日 2026-11-02 已 140 天，超过 90 天时效要求
    证据：出具日期 2026-06-15｜入职日 2026-11-02
    依据：《员工入职管理办法》第 3.5 条：入职体检报告须为入职前 90 日内出具。

[不通过] [HIGH] HR-006 材料证件号码一致性  (置信度 1.00｜deterministic)
    说明：DOC-002 学历证书 证件号与登记身份证号不一致，需核实是否为同一人
    证据：材料证件号 310101199008123170｜登记证件号 310101199008123017
    依据：《员工入职管理办法》第 3.3 条：材料上的证件号码须与候选人登记的身份证号一致。
```

每条判定固定带三样东西——**说明（为什么判）、证据（依据哪一行数据）、依据（制度第几条）**。
这是业务方肯签字的前提，也是它和"让 AI 看一眼"的本质区别。

## 和常见做法差在哪

| | 常见做法 | 本项目 |
|---|---|---|
| **判断方式** | 全部交给模型 | 确定性规则用代码，语义判断用模型，**模型不碰任何可计算的量** |
| **结论形态** | 一句"建议通过 / 不通过" | 每条带 `evidence` + `basis`，可追溯、可申诉 |
| **拿不准时** | 硬给一个答案 | 置信度低于阈值一律转人工，**绝不硬判** |
| **稳定性** | 同一单据两次结论可能不同 | 温度固定 0，同输入同输出 |
| **换业务域** | 重写一套 | 只改数据模型、校验器、Prompt 三处，引擎全复用 |

## 同一套引擎，两个业务域

两个域共用一个编排引擎，用来证明底座的可复用性——不是两个独立项目拼在一个仓库里：

| 业务域 | 审核对象 | 决策口径 |
|---|---|---|
| **费用审核** | 一张报销单（`ExpenseReport`） | 通过 / 转人工复核 / 退回补正 |
| **HR 入职材料审核** | 一个候选人的入职材料包（`OnboardingRecord`） | 可办理入职 / 转 HR 人工复核 / 退回补正 |

> **加一个业务域要改什么？只有三件事**——数据模型、校验器、Prompt。
> 引擎编排、规则加载、模型客户端、决策分级、留痕全部复用。
> HR 域就是这么加进来的，全程没有改动 `app/audit.py` 的一行审核逻辑。
> 这是这套东西真正的资产：**底座不变，换个域就能再交付一次。**

> [!IMPORTANT]
> **本仓库不含任何真实数据。** `samples/` 里的姓名、证件号、公司名、发票号全部为虚构，
> 身份证号均未通过校验位算法，不对应任何真实个人。仓库内无 API Key、无内网地址、无个人信息。
> 生产环境的使用边界见 [数据与合规声明](#数据与合规声明)。

## 批量模式：Excel 进，Excel 出

前面两种形态（命令行、HTTP 接口）都要求有人愿意打开终端或网页。
但真实场景里，HR 不会为了查一次材料合规性去打开一个陌生网址——**他们会打开一个别人发来的 xlsx 附件。**

所以这里还有第三种形态，也是**最容易真正被用起来的那一种**：不做服务、不做部署，直接读写 Excel。

```bash
# 1. 生成模板（含两个示例行 + 填写说明）
python batch_audit.py --init-template 入职材料审核_模板.xlsx

# 2. 填好后批量审核
python batch_audit.py 入职材料审核_模板.xlsx
# → 生成 入职材料审核_模板_审核结果.xlsx

# 3. 也可以指定输出、限定记录号区间、换规则库
python batch_audit.py 10月校招.xlsx -o 检查结果.xlsx --from RZ-2610-001 --to RZ-2610-050
```

输入两张表，靠 `记录号` 关联：

| 工作表 | 一行代表 | 关键列 |
|---|---|---|
| `人员` | 一个候选人 | 用工形式（决定必备清单）、拟入职日期（时效基准）、是否应届生（决定豁免） |
| `材料` | 一份材料 | 材料类型（须与规则库名称一致）、签发日期、有效期至、材料上姓名/证件号、备注 |

输出三张表：

| 工作表 | 内容 | 给谁看 |
|---|---|---|
| `汇总` | 每人一行：结论色块 + 高危/一般/预警计数 + 一句话说明 | HR 负责人，扫一眼就知道谁要处理 |
| `问题明细` | 每条问题一行：说明 / 证据 / 依据 / 置信度 | 具体办理的人，照着这条去补材料 |
| `统计` | 通过率 + **规则命中排行** | 你自己汇报时用——哪个环节最容易出错，一眼可见 |

> `统计` 页的「规则命中排行」是这个工具最容易被低估的部分。
> 它回答的不是"谁不合规"，而是"**你们入职流程里哪个环节系统性出错**"。
> 跑 50 份历史材料，如果 HR-003（体检报告超 90 天）命中 30 次，
> 那结论就不是"这些人不细心"，而是"通知入职的时间点太晚"——这是流程问题，不是人的问题。

## 核心设计：为什么必须分两层

这是整套方案最重要的一个决定，也是跟客户讲方案时的主线。

| 判断类型 | 例子 | 由谁执行 | 为什么 |
|---|---|---|---|
| **确定性判断** | 金额是否超限、发票号是否重复、消费日期是否在行程内、发票抬头是否一致 | Python 代码 | 这类判断**必须** 100% 可复现。同一个数字，今天算和明天算结论必须一样。用大模型算金额是工程事故 |
| **语义判断** | 事由与费用类型是否匹配、是否疑似拆单、是否属于可报销范围 | 大模型 | 这类判断没有确定性算法，人审也是凭经验。模型的优势正好在这里 |

**大模型不参与任何可以计算的判断。** 这句话有两个作用：

1. 技术上：把不可控的环节压到最小，系统整体可靠性大幅提升。
2. 商务上：财务最怕的就是"AI 乱判"。你能明确说出"金额和日期这些是代码算的，不是模型猜的"，
   信任门槛会瞬间降低一大截。

另外三条让财务敢用的设计：

- **温度固定为 0**：同一张单据两次审核，结论必须完全一致
- **每条判定都带 `evidence` + `basis`**：引用具体单据编号和制度条款原文，员工可以申诉，财务可以复核
- **拿不准就转人工**：置信度低于阈值、或模型输出 `uncertain`，一律进人工复核队列，绝不硬判

## 改规则：不需要动代码

这是相对硬编码规则引擎最大的差异点。**加一条规则 = 往 YAML 里加一段。**

```yaml
  - id: TRV-005
    name: 加班餐费标准
    category: 差旅费
    severity: medium
    scope: item
    evaluator: "builtin:amount_limit"          # 确定性校验器
    basis: "《员工差旅费用管理办法》第 5.1 条：加班餐费人均不超过 80 元。"
    description: "加班餐费人均不得超过 80 元。"
    applies_to_categories: [加班餐费]
    params:
      mode: per_person
      limit: 80
```

改完存盘、重启服务即可生效，**不需要重新打包、不需要发版**。
对客户来说这意味着"业务规则自己就能维护"，是很强的谈判筹码。

### 需要语义判断时

```yaml
  - id: SEM-004
    name: 是否与业务场景相关
    severity: medium
    scope: report
    evaluator: "llm:semantic"
    basis: "《费用报销票据管理规定》第 1.3 条：报销费用须与公司业务直接相关。"
    description: "判断每条明细的支出是否与申请人岗位及业务场景存在合理关联。"
```

`llm:semantic` 的规则会被自动打包进同一个请求发给模型，
**一次调用审核全部语义规则**，而不是一条规则一次请求 —— 成本差好几倍。

### 需要新的确定性计算逻辑时

在 `app/checkers.py` 里加一个函数，注册进 `CHECKERS`，然后在 YAML 里引用：

```python
def check_my_rule(rule: Rule, report: ExpenseReport) -> list[RuleVerdict]:
    verdicts = []
    for item in (i for i in report.items if rule.applies_to(i)):
        ...
    return verdicts

CHECKERS = {
    ...
    "my_rule": check_my_rule,   # YAML 里写 evaluator: "builtin:my_rule"
}
```

## HR 域：同一套骨架的第二次复用

费用域证明"AI 能审钱"，HR 域证明"底座能复用"。两个域的技术分层完全一样，
只是把"能不能报销"换成了"这份入职材料能不能办入职"。

### 审什么

| 判断类型 | HR 域的例子 | 由谁执行 |
|---|---|---|
| **确定性判断** | 必备材料是否齐全（按用工形式）、体检报告是否在入职前 90 天内出具、证件有效期是否覆盖入职日、材料证件号与登记身份证号是否一致、材料姓名是否与候选人一致、offer 日期是否早于入职日 | Python 代码 |
| **语义判断** | 材料构成与用工形式是否匹配（实习生该签实习协议而不是劳动合同）、备注里是否有"仅提供复印件/原件未交/待盖章"这类证据瑕疵、候选人自报信息与材料是否矛盾 | 大模型 |

### 三条只有一线 HR 才知道的规则（已配置化，改 YAML 即可）

1. **不同用工形式的必备清单不同。** 全职要身份证/学历证书/离职证明/体检报告/银行卡/劳动合同；
   实习生要的是学生证和实习协议，不是劳动合同；外包只要身份证和银行卡。
   把实习生的清单套到全职上，或者反过来，都会出事。
2. **有豁免条款。** 应届毕业生没有前雇主，按制度免交离职证明。
   规则引擎如果不认这条，就会把每一份校招材料都判成不合规 —— 这是最容易被做错的地方。
3. **不同材料的时间窗不同。** 体检报告要求入职前 90 日内出具；
   离职证明原则上不得晚于入职日（否则存在未解除前一段劳动关系的风险）。

这三条在 `config/rules_hr.yaml` 里都是参数，HR 自己就能改：

```yaml
  - id: HR-001
    name: 必备材料齐全性
    severity: high
    evaluator: "builtin:hr_required_docs"
    params:
      required_by_type:
        全职: [身份证, 学历证书, 离职证明, 体检报告, 银行卡, 劳动合同]
        实习: [身份证, 学生证, 实习协议, 银行卡]
      exempt_rules:
        - doc_type: 离职证明
          when_field: is_fresh_graduate
          when_value: true
          note: 应届毕业生免提交离职证明
```

### HR 域的三条决策路径（已实跑验证）

| 样例文件 | 场景 | 结论 |
|---|---|---|
| `samples/onboarding.json` | 缺离职证明与劳动合同、体检报告超出 90 天、学历证书证件号对不上、备注"仅提供复印件" | **REJECT 退回补正**（退出码 3） |
| `samples/onboarding_clean.json` | 校招应届生，材料齐全，离职证明按制度豁免 | **APPROVE 可办理入职**（退出码 0） |
| `samples/onboarding_review.json` | 体检报告未填出具日期，无法判断时效 | **MANUAL_REVIEW 转 HR 人工复核**（退出码 2） |

最后一条是这套系统最重要的设计：**信息不足时不猜，直接转人工。**
HR 最怕的不是系统说"不通过"，是系统说"可以"但其实它并不知道。

### 为什么 HR 场景比费用场景更适合做第一个落地

- **数据敏感度更低**：入职材料的字段可以脱敏（姓名、证件号用假数据即可演示），
  谈演示时阻力比"把报销数据给我"小得多；
- **判断更依赖制度而非金额**：几乎全是"符不符合规定"，规则的确定性成分更高；
- **复核成本极低**：HR 看到结论可以直接翻档案核对，5 秒就能验证系统对不对 —— 这是建立信任最快的方式。

> ⚠️ 合规提示：入职材料含敏感个人信息。实际上线前必须完成脱敏、告知与留痕改造，
> 且数据不出内网（走本地模型部署）。详见 [数据与合规声明](#数据与合规声明)。

## 接入客户系统（旁路集成）

**永远不要动客户的核心费控系统。** 旁路只读接入，风险最低，客户最容易点头。

```
客户现有系统（用友 / 泛微 / 金蝶 / 自研 OA）
      │  报销单提交时，POST 一份 JSON 过来
      ▼
POST /audit  →  { decision, verdicts[] }
      │
      ├─ APPROVE        → 正常进入审批流
      ├─ MANUAL_REVIEW  → 打回人工复核节点
      └─ REJECT         → 退回申请人补正
```

字段映射在调用方做一次转换即可，审核逻辑完全不用改。接口列表：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/health` | 健康检查，含当前模型与规则版本 |
| GET | `/rules` | 查看费用域当前生效的全部规则 |
| POST | `/audit` | 审核一张报销单 |
| POST | `/audit/batch` | 批量审核（上限 20 张/次） |
| GET | `/audit/logs` | 查看审核留痕 |
| GET | `/hr/rules` | 查看 HR 域当前生效的全部规则 |
| POST | `/hr/audit` | 审核一份入职材料包 |
| POST | `/hr/audit/batch` | 批量审核（上限 20 份/次） |
| GET | `/hr` | HR 域演示页 |

完整交互式文档：`http://localhost:8000/docs`

## 客户私有化部署

中大型客户不会允许报销数据出内网，所以本地部署能力是**准入条件**而不是加分项。

```bash
# 客户机房：模型走本地，数据不出域
LLM_PROVIDER=ollama
LLM_BASE_URL=http://localhost:11434/v1
LLM_MODEL=qwen2.5:14b
```

也支持任意 OpenAI 兼容协议的私有推理服务（vLLM / TGI / 各家一体机），
把 `LLM_BASE_URL` 指过去即可。

Docker 化建议：应用镜像 + 独立的模型服务镜像，两者通过内网通信，
应用容器挂载只读的 `rules.yaml` 和可写的 `logs/` 卷。

## 成本估算

单张单据（10 条明细）大约消耗 2500–3500 输入 token、600–900 输出 token。
按 2026 年国产模型 1–4 元/百万 token 的价格区间，**单张审核成本约 0.005–0.02 元**。

一家月均 2000 张单据的企业，模型成本在 **10–40 元/月**。
而人工审核 2000 张单大约需要 1.5–2 个人天。这个对比就是报价时最有力的数字。

私有化部署时成本结构变为显卡折旧，需要另行测算 —— 但客户通常更在意数据合规，愿意为此付费。

## 数据与合规声明

### 本仓库的数据

仓库内所有业务数据均为**虚构样例**，不对应任何真实个人或企业：

| 字段 | 说明 |
|---|---|
| 姓名（张伟、李思远、周雨桐等） | 虚构 |
| 身份证号 | 虚构，**均未通过 GB 11643 校验位算法**，不可能是真人号码 |
| 公司名 / 统一社会信用代码 | `示例科技有限公司`、`91310000MA1FLXXXXX`，占位 |
| 发票号、银行卡、体检机构 | 占位或泛称 |
| 制度条款（`basis` 字段） | 通用模板表述，非任何一家企业的制度原文 |

**代码中不存在**：API Key 或任何凭证（一律从 `.env` 读取）、内网地址、真实域名账号、
开发者个人信息、企业内部系统名称。

`logs/` 目录已被 `.gitignore` 排除。它会记录每次实际提交过的单据，
**接真实数据后属于业务敏感数据，不应进版本库**。

### 接入真实数据前必须做的

输入的是员工或候选人的材料时，这些属于《个人信息保护法》下的个人信息，
其中身份证号、体检信息、银行账号属于**敏感个人信息**：

1. **最小化采集**——只传审核判断必需的字段，材料原件不落盘、不入库
2. **字段脱敏**——身份证号、手机号、银行账号在日志与界面中一律掩码；
   审核结论只需要"证件号是否一致"这个布尔结果，**不需要存明文**
3. **数据不出内网**——接本地模型（`LLM_PROVIDER=ollama` 或私有化部署）。
   把员工材料发给公网模型 API，在多数企业是明确的合规红线
4. **留痕脱敏**——`logs/*.jsonl` 默认写入完整判定内容，生产环境需改造为只落
   单据 ID 与判定码，或加密存储并设置保留期限
5. **告知与授权**——采集目的、范围、保存期限需向员工告知并取得同意
6. **权限隔离**——多部门/多法人场景下，谁能看哪份材料必须严格隔离

### 责任边界

本系统输出为**审核辅助意见**，不构成最终审批决定。系统刻意设计为
"拿不准就转人工"，最终审批责任始终在人工。接入生产系统时，
应在合同与内部制度中明确这一点。

## 上线到客户现场前必须补的东西

这是一个骨架，离"能装到客户生产环境"还有这些距离，别跳过：

1. **历史数据回测**：拿客户过去 6 个月的真实单据跑一遍，量出准确率和漏报率。
   没有这个数字，客户不会签合同 —— 这也是免费 POC 阶段最该做的事。
2. **发票真伪查验**：目前只做格式和一致性校验，真实场景需要接国家税务总局查验接口。
3. **历史重复报销检测**：`duplicate_invoice` 现在只查单据内部，要扩到查询历史库。
4. **规则版本管理与灰度**：规则改动要留版本号，支持按部门灰度生效、支持随时回滚。
5. **人工复核工作台**：`MANUAL_REVIEW` 的判定需要有地方给人看、给人改、给人留反馈。
   这些反馈是后续优化 Prompt 和规则的原材料。
6. **权限与数据隔离**：多部门/多法人场景下，谁能看到哪张单，必须做严格隔离。
7. **可观测性**：模型调用失败率、平均耗时、token 消耗要能监控和告警。
8. **免责边界**：合同里写清楚系统输出是**辅助意见**，最终审批责任在人工。
   这条既是合规要求，也是保护你自己。
9. **HR 域特有**：入职材料含个人敏感信息，上线前必须完成脱敏、告知、留痕改造。
   完整清单见 [数据与合规声明](#数据与合规声明)。

## 站在客户面前可以这么说

> 系统分两层跑。金额、日期、发票这些能算准的，用代码算，结果和人工核对完全一致，
